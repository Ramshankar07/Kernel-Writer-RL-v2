# 30 follow-up questions, with answers

All numbers: Modal re-run, Sept 2026. Source: `results/numbers.json` (generated by `modal_app/analyze.py`). Figures: `presentation/figures/`.

## A. Setup and motivation

**1. What problem does this project solve?**

It trains an LLM agent to write faster GPU kernels with RL from verifiable rewards (RLVR). The agent proposes a full Triton `kernel.py`, a GPU benchmark checks correctness and speed, and the agent revises. Reward = log2(best speedup) if any proposal PASSes, else 0.

*Evidence:* `src/autokernel-rlvr/agent_loop/reward.py`, figure 01

**2. Why did the project start on KernelBench v1?**

KernelBench Level 1 is the standard public benchmark (100 single-op PyTorch problems, fast_p metric), so it served as the first test set. The re-run rebuilt that harness on Modal: an identity solution (ModelNew = Model) PASSes 58/100 problems with median measured speedup 1.000× (p5–p95 1.000–1.007×), so the timing is trustworthy. Benching the same identity solution twice on problems 1–50 gave the same verdict on 41/50 and a median speedup difference of 0.001×. 55 problems are harness-valid.

*Evidence:* `modal_app/kernelbench_modal.py::sanity`, figure 03

**3. Why move from KernelBench to AutoKernel's 9 kernel types for RL?**

Validity first, then cost. Only 55/100 KernelBench L1 problems are harness-valid in AutoKernel's KernelBench mode: 35 conv problems fail even for an identical model (weight init isn't seeded), and 9 large-input problems time out intermittently. Cost: a KB bench has median 20.94 s and p95 110.21 s on H100, vs AutoKernel's p50 5.95 s / p95 33.46 s on the 5× cheaper L4. RL needs thousands of rewards, so AutoKernel's 9 kernels became the training set and KernelBench the held-out eval.

*Evidence:* `results/kb_sanity.jsonl`, `results/stage1_baselines.jsonl`

**4. Which model, and why that size?**

Qwen2.5-Coder-7B-Instruct (same as the original design). 7B fits vLLM rollout on one H100 and a LoRA (r=64, 161.5M trainable params) trainer on a second H100, which with 8 bench GPUs is exactly the 10-GPU account limit.

*Evidence:* `modal_app/train_grpo.py`, `modal_app/policy.py`

**5. What changed between the original design and this re-run?**

Original (Apr 2026): 3 SkyPilot clusters: 8×H100 verl trainer, FastAPI+Redis queue, A10/L4 spot workers, about $27/hr per the README. Re-run (Sept 2026): Modal with ≤10 GPUs, i.e. 1×H100 LoRA trainer + 1×H100 vLLM policy + ≤8×L4 bench, and a modal.Dict content-hash cache instead of Redis. The GRPO math follows verl (group-normalized advantage, token-mean loss, no KL). All original results were lost, so every number here is from the re-run.

*Evidence:* figure 01, `CLAUDE.md`

## B. Verifier and reward

**6. How noisy is the reward signal?**

Very quiet. Re-benching the same starter kernel 3× gives at most 1.89% coefficient of variation in speedup across 9 kernels × 2 GPUs. On KernelBench the identity solution measures 1.000× median.

*Evidence:* `results/stage1_baselines.jsonl`

**7. Can the agent game the benchmark with the quick mode?**

Yes, which is why reward uses the full bench. `bench.py --quick` skips the numerical-stability stage. The flash_attention, rmsnorm starters PASS quick (e.g. rmsnorm 5.096× on H100) but FAIL full, so a quick-mode reward would pay for numerically unsafe kernels.

*Evidence:* figure 02, `modal_app/agent_eval.py::run_episodes`

**8. Does the log2 clip at 3.0 (8×) matter?**

Not at this stage. Of 25 passing trajectories in the base-model eval, 0 hit the +3 ceiling and 0 hit the −1 floor. The best base-model speedup was 2.9×. The clip is insurance for later training, not an active constraint.

*Evidence:* `reward.py:SPEEDUP_CLIP_HIGH`, `modal_app/analyze.py::ablations`

**9. Is there a flaw in the reward design?**

Yes: a correct kernel slower than PyTorch gets log2(s) < 0, which is worse than never passing (0). In the base eval 13/25 passing trajectories were slower than PyTorch and got negative reward (e.g. a 0.99× reduce kernel scores −0.015), so within a GRPO group a correct-but-slow kernel ranks *below* a crash. A fix is max(0, log2 s) + a small PASS bonus.

*Evidence:* `reward.py` lines computing `reward = math.log2(...)`

**10. Would per-step shaping (+0.02/PASS, −0.02/CRASH) help?**

It changes the learning signal a lot. Offline on the base-model trajectories it changes the ordering or tie-status of 108/164 within-group trajectory pairs, because many groups are otherwise all-zero ties. It adds signal but also rewards spamming trivially-correct kernels (README sharp edge #6). Left off, as in the original.

*Evidence:* `modal_app/analyze.py::ablations`

## C. Base model (before RL)

**11. How good is the untrained model?**

Weak. Over 9 kernels × 8 samples × 8 turns on L4, 34.7% of episodes produce at least one PASS, fast_1.0 = 15.3% (correct *and* faster than PyTorch), mean reward 0.1327. Only 4/9 kernels are ever solved.

*Evidence:* figure 05

**12. Does giving the model more turns help?**

Barely. pass@1 turn = 31.9% vs pass@8 turns = 34.7%. With the original log-tail feedback it was flat: 30.6% → 30.6%. The base model doesn't use feedback well, which is the gap RL is supposed to close.

*Evidence:* figure 04

**13. Why do generated kernels fail?**

numerical mismatch 258 (54%); Triton API / compile error 128 (27%); out of shared memory 27 (6%) of 475 non-PASS turns. Correctness, not speed, is the bottleneck.

*Evidence:* figure 06

**14. Does the format of the benchmark feedback matter?**

Yes, and this was a bug in the original design. The worker returned the *tail* of bench.py's log, which is only the summary block, so the model never saw which check failed. Sending the failure lines instead (v2) moved episode pass rate 30.6% → 34.7%, mean reward 0.0966 → 0.1327, CRASH turns 128 → 56, and solved rmsnorm (2.9×) for the first time. No training involved.

*Evidence:* figures 04–05, `agent_eval.py::observation`

**15. Does the model just repeat itself?**

Often. 61.1% of turns resubmit code already tried in the same task (52.9% bench-cache hit rate), mostly re-sending the starter kernel after a failure. The content-hash cache makes that free, and it is also a measurable target for RL.

*Evidence:* `bench_modal.py::cache_key`

## D. GRPO training

**16. Did RL with the original reward improve the agent?**

Barely. Over 18 GRPO steps (v1), the original reward went 0.0981 → 0.1147 (mean of first vs last 3 steps), and the pass rate went 29.2% → 25.0%. The gain came from reduce (fewer much-slower passing kernels: -0.12 → -0.005) and cross_entropy. 5/9 kernels (flash_attention, fused_mlp, layernorm, matmul, rotary_embedding) never passed in any episode of any step; rmsnorm passed only occasionally.

*Evidence:* figure 09, `results/grpo/grpo_v1/metrics.jsonl`

**17. Why did v1 stall?**

No gradient. On average 65.4% of groups had identical rewards across all 8 samples, so their GRPO advantage is 0. The never-solved kernels can't teach anything under a pass/fail terminal reward. There is a second, quieter issue: in the groups that do vary, the spread is often bench timing noise (std ≈ 0.002), which std-normalisation inflates to full ±1 advantages.

*Evidence:* figure 09, `train_grpo.py::grpo_advantages`

**18. What did reward v2 change, and did it help?**

Reward v2 does two things: (a) partial credit for correctness progress (smoke test, fraction of shape configs passed, stability; max 0.3), and (b) any PASS scores ≥0.5, fixing the slower-than-a-crash floor. It also ignores groups with std < 0.02, the measured noise floor. Over 10 steps: reward_v2 0.3713 → 0.3985, original reward 0.1066 → 0.1154, pass rate 31.5% → 31.9%, zero-advantage groups 37.8% (v1: 65.4%), smoke-test pass rate 41.9% → 43.9% (v1: 42.9% → 42.1%). Honest reading: the robust effect is more groups with gradient, and the pass rate no longer declines as it did in v1. The reward changes are small and single-seed, and no new kernel was solved in 10 × 72 episodes (kernels ever passed: cross_entropy, reduce, rmsnorm, softmax).

*Evidence:* figure 09, `modal_app/reward_v2.py`

**19. Why a GRPO group size of 8?**

Measured on base-model rollouts: zero-advantage groups are 69.3% at group=2, 60.4% at 4 and 55.6% at 8. Group=4 would waste roughly 4.9% more of each batch.

*Evidence:* figure 07

**20. What does one training step cost?**

~445 s rollout (72 episodes × 4 turns, bench-bound) + ~32 s policy update. H100 time: v1 18 steps = 2.38 h ≈ $18.84; v2 10 steps = 1.41 h ≈ $11.15 (2 H100s at $3.95/GPU-hr), plus the L4 bench pool. The bench cache served 45.2% of v1's late-training benchmarks for free. The trainer GPU idles about 93% of each step, so async rollouts are the obvious next win.

*Evidence:* `results/grpo/*/metrics.jsonl`

## E. Evaluation and generalization

**21. Does training on 9 AutoKernel kernels transfer to KernelBench?**

No. On a 28-problem KernelBench L1 subset (every 2nd harness-valid problem, 3 turns), the base model gets fast_0 = 0.0% and fast_1.0 = 0.0%; after GRPO v2: fast_0 = 0.0%, fast_1.0 = 0.0%. So no measurable transfer from 9 AutoKernel kernels in 10 steps. Top failure reasons for the base model: Triton API / compile error 54/84; numerical mismatch 20/84; API/name error 5/84. A 7B model can't yet produce a correct KernelBench `ModelNew` in Triton within 3 turns; most failures are calls to Triton APIs that don't exist in Triton 3.2, so API grounding comes before speed.

*Evidence:* figure 10

**22. Does the GPU matter for the reward?**

A lot. The same starter softmax is 1.906× on H100 but 0.868× on L4; flash_attention passes quick mode on H100 but runs out of shared memory on L4 (101 KB limit). Rewards are measured on L4, like the original A10/L4 worker pool.

*Evidence:* figure 02

**23. How do you know the agent isn't gaming the verifier?**

Four guards. (1) Full 5-stage correctness (smoke, shape sweep incl. fp32, numerical stability, determinism, edge sizes) on every reward. (2) The reference is AutoKernel's fixed `reference.py`, and the agent only writes `kernel.py`. (3) Content-hash cache, so the same code always gets the same reward. (4) The quick-vs-full gap (B2) shows why cheaper checks would be exploitable.

*Evidence:* `results/autokernel_src/bench.py`

**24. Does context length become a problem?**

It grows ~1.5k tokens per turn (2209 → 12390 prompt tokens over 8 turns), because each turn resends a full kernel.py plus bench output. That's why training uses 4 turns and a 32k context.

*Evidence:* figure 08

**25. Would early stopping save compute (README sharp edge #7)?**

Hardly, for this model. Stopping once speedup > 2× after turn ≥ 5 saves only 1.6% of turns and loses 0.0 total reward, because the base model rarely reaches 2×. Reward by turn budget: 0.0967 at 1 turn vs 0.1327 at 8.

*Evidence:* `modal_app/analyze.py::ablations`

## F. Engineering and next steps

**26. What broke when the project was re-run?**

Five real bugs: (1) the worker called `bench.py --kernel-type`, but the flag is `--kernel`; (2) the worker parsed `results.tsv`, which bench.py never writes (metrics are on stdout); (3) AutoKernel's KernelBench starter keeps `super(Model, self)` after renaming the class, so all 100 starters crash; (4) KernelBench times CPU input generation inside a 30 s trial timeout, so with default Modal CPUs only 55% of identity runs passed; (5) KernelBench mode never seeds weight init, so 35 conv problems can't pass even as an identical model. Plus two of mine: vLLM 0.8.5 needed a transformers pin, and my first problem listing read the cache's .json metadata files as problems (caught and re-run).

*Evidence:* `CLAUDE.md` › Findings

**27. What does it cost?**

Original design: about $27/hr (README, 8×H100 on-demand). Re-run: ≤10 Modal GPUs, about $14.3/hr at full load (2×H100 + 8×L4 list price). GRPO: v1 $18.84 (18 steps), v2 $11.15 (10 steps) in H100 time.

*Evidence:* `modal_app/analyze.py` prices

**28. What happened to the AMD MI300X path?**

It is design-only. The repo has an MI300X reward (`reward_amd.py`, per-kernel clip 4.0 for FP8/MXFP4) and worker (`worker_amd.py`, ROCm env, 300 s timeout), but Modal offers no AMD GPUs and the upstream AutoKernel repo has no `amd-hip` branch, so none of it could run.

*Evidence:* `src/autokernel-rlvr/agent_loop/reward_amd.py`

**29. Why not use verl, as in the original design?**

verl's ToolAgentLoop API drifts between 0.5 and 0.7 (README sharp edge #1), and its Ray + vLLM colocated setup expects a multi-GPU node. The re-run keeps verl's GRPO semantics (adv_estimator=grpo, token-mean loss, no KL, one on-policy update) in ~250 lines, and calls the original `reward.py` unchanged.

*Evidence:* `modal_app/train_grpo.py` docstring

**30. What would you do next?**

(1) Fix the reward floor: correct-but-slow should not be worse than crashing. (2) Keep the v2 failure-line feedback (a free gain). (3) Curriculum: oversample the 5 never-solved kernels once the model reliably passes the easy ones, since all-zero groups give no gradient. (4) Async rollouts so the trainer GPU isn't idle. (5) Evaluate on KernelBench L2 fusion problems.

*Evidence:* sections B–D
