SFT before RL

GRPO on a 7B coder model barely moved, because most rollout groups either all failed or all passed, so there was little to learn from. We went back and ran supervised fine-tuning (SFT) first: fix the parts of the setup that were not the model's fault, build a GPU-verified Triton SFT set, train a LoRA, and check whether RL would now have a usable signal. Correctness improved a lot. Speed did not.

Why SFT, and not more GRPO

We sorted every failing turn from the GRPO v1/v2 and agent-eval rollouts by the earliest stage that failed: 9,393 benchmarked turns in 2,225 trajectories, of which 8,267 failed. Three findings argued for SFT:

  • The reward never saw a real speedup. Re-scored under the fixed bench v2, no GRPO kernel beat its starter.
  • Many failures were basic. 31.3% of failing turns were Triton compile errors. 30% of those used APIs that do not exist in Triton 3.2, for example tl.math.tanh (281 times). After a compile failure, the next turn passed only 1.2% of the time.
  • The model got stuck. In 54.5% of consecutive fail→fail pairs, the model repeated the same error, and 29.2% of pairs resubmitted byte-identical code. RL cannot learn from groups that never succeed.

So the plan was: teach format, API use, and repair with verified supervised data first, then resume GRPO only if the SFT model passed explicit gates.

Sources: results/v3/sft_failure_analysis.md, results/v3/sft_plan.md.

Phase 0: remove failures that were not the model's fault

Before measuring the model again, we fixed three problems in the setup itself. Each change is a new file; no old harness, prompt or result file was edited.

  • Three broken starters. Under bench v2, the upstream fused_mlp starter crashed (Triton 3.2 resolves the unused tl.math.tanh branch, so the fix uses tanh(y) = 2·sigmoid(2y) − 1). flash_attention ran out of shared memory on the L4 (101,376 B), and matmul's fp32 path used TF32 (max error 4e-2 against a tolerance of 1e-4). All 9 starters in modal_app/starters_v2/ now PASS. The exception is 3 fp32 matmul cases at K = 4096–8192, which an exact fp64 matmul also fails, because bench v2's golden for them is itself fp32.
  • Prompt v2. The v1 system prompt described a callable tool, but the parser expected a fenced code block. v2 describes only the fenced-block protocol. Tool calls written as code fell from 7.1% of failing turns to 0.4% (2/497). Malformed or unterminated code fences did not fall (90 turns, 18.1% of failures), and the comparison is not like-for-like: the problems, bench and starters were all new.
  • A held-out validation set. 62 problems with 376 correctness cases, covering all 9 AutoKernel families with new shapes and variants (layernorm without bias, rmsnorm at N=16384, online softmax over 300k–1M columns, rotary with head_dim 80/96, bf16, GQA…). No KernelBench problems are in it. Its harness adds a launch check (a PASS must launch an @triton.jit kernel) and uses fp64 goldens for fp32 inputs of matmul, attention and MLP. It also computes softmax and cross-entropy goldens in fp64 on the CPU, because CUDA fp64 softmax in torch 2.6 gives wrong values when 257 < n ≤ 1024 and n % 8 == 1.

Filter and verification funnel

Static filter: the code parses; at least one @triton.jit kernel is actually launched; there is no torch.nn.functional, torch.matmul or try/except fallback in the forward path; and tl.* symbols are checked against a Triton 3.2 allowlist (the verifier rejects the rest as REJECT_SYMBOL). GPU verification on ≤4 L40S/L4 containers: an fp32 golden reference, 3 seeds × 2 shapes, extreme-magnitude inputs for reductions, and a launch check (no silent PyTorch fallback). Decontamination: rows whose PyTorch module is a near-duplicate (normalized AST, or ≥ 50% of distinctive lines) of a KernelBench L1 or validation problem were dropped. Op-level overlap (shared torch ops) was only tagged, not dropped: 673 training examples share most of their ops with some KernelBench L1 or validation problem. Examples longer than 4,096 tokens were dropped.

Why the yields differ:

  • Dr. Kernel: most losses come from the static filter (mostly try/except fallback paths and torch.nn.functional calls in the forward path). The GPU verifier dropped about 9% more (FAIL 123, silent PyTorch FALLBACK 116), and decontamination removed 19 KernelBench L1 near-duplicates.
  • Dr. Kernel repair: mostly lost to the 4,096-token limit (294 too long).
  • KernelBook: its targets are TorchInductor output, which hard-codes shapes, so 689 fail on the second shape. We dropped them deliberately.

"In train" is below "kept" for Dr. Kernel because the mix capped generic families (other, activation, reduce, conv) at 80% of single-turn examples and repair data at 15% of the mix, so not every verified example was used. It exceeds "kept" for KernelBook because scarce families (MLP, attention) were upsampled up to 3×. 60 examples went to the dev split.

Why GRPO was not resumed

The gates passed, but the offline check showed that only 2 of 126 solved SFT episodes beat the starter by more than 5%. A speed-shaped GRPO reward would have had almost nothing to reinforce beyond correctness, which SFT had already improved. Given that, and the limited remaining compute budget, we decided (2026-10-07) not to resume GRPO.

Caveats

  • Speed did not improve. SFT raised correctness (pass@1, compile errors, KernelBench Triton PASS) but not speed. The beat-starter rate went slightly down, and the geomean speedup vs starter is about 1.00×.
  • Dr. Kernel data is GPT-5-distilled. drkernel-coldstart-8k has an MIT tag on Hugging Face, but its paper says the trajectories were distilled from GPT-5, so OpenAI's output terms (no use to develop competing models) may apply. We treat it as research-only. It supplies 2,707 of the 3,022 training examples.
  • The SFT datasets are not published. The repo has the scripts to regenerate them from the pinned revisions (modal_app/sft_ingest_drkernel.py and the other ingest scripts, sft_verify_modal.py, sft_decontam.py, sft_assemble.py), plus the summary reports in results/v3/sft/. The trained adapter is not published either.
  • Small samples. The validation results use n=4 per problem, from two independent n=2 runs. KernelBench uses n=1, so one sample per problem.
  • A different harness from the earlier results. These numbers come from bench v2 / the val harness / kb v2. They are not directly comparable with the original-bench numbers on the RL results page. See Verifier.
